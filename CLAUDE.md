# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Android XO (tic-tac-toe style) game in Kotlin with AdMob ads. Source packages are `com.m7mdabaza.xogame.*`, but the published `applicationId` is `com.m7mdabaza.x_ogame`. Don't "fix" this mismatch, because changing the applicationId breaks Play Store updates.

v2 (the rewrite, `docs/UPGRADE_PLAN.md`) is done. v3 is in progress on branch `feature/v3-upgrade`: a "No ads" badge with a Remove-ads dialog, and two-phone play over Nearby Connections. Its plan and milestones are in `docs/UPGRADE_PLAN_V3.md`. Do not commit or push unless the user explicitly asks.

## Build / test

The toolchain is AGP 9.5.0 (built-in Kotlin, so there is no `kotlin-android` plugin), Gradle 9.8.2 wrapper, Kotlin 2.4.21, KSP + Hilt, compileSdk 37 (needed by current Compose/AndroidX), targetSdk 36, and minSdk 24 (required by Google Mobile Ads 25). All versions live in `gradle/libs.versions.toml`; build scripts are Kotlin DSL. AGP 9 needs JDK 17+. In Git Bash: `export JAVA_HOME=~/.jdks/jbr-21.0.11`. In Studio, set the Gradle JDK to 17 or 21. `buildFeatures.resValues` must stay on in `:app` because the AdMob IDs are resValues.

```sh
./gradlew assembleDebug                 # build debug APK
./gradlew installDebug                  # install on connected device/emulator
./gradlew test                          # all JVM unit tests (every module)
./gradlew :domain:test                  # pure-Kotlin domain tests only (fast)
./gradlew :data:test                    # DataStore repository tests (JVM, temp files)
./gradlew :domain:test --tests "com.m7mdabaza.xogame.domain.model.BoardSizeTest"   # single test class
./gradlew connectedAndroidTest          # instrumented tests (needs device)
./gradlew :presentation:connectedDebugAndroidTest   # Compose UI tests + accessibility checks (needs device)
./gradlew lint
./gradlew :app:assembleRelease          # minified release APK (unsigned); bundleRelease for the Play AAB
```

Release builds run R8 (`isMinifyEnabled` + `isShrinkResources`); app rules are in `app/proguard-rules.pro` (line numbers kept for Play crash reports, one `-dontwarn` for review-ktx). WorkManager 2.12 is used by `:presentation` (daily reminder) and also declared in `:app` on purpose: the ads SDK pulls in 2.7, whose old keep rules let R8 strip Room's constructor and the release build crashed at startup. The bundle's language split is off (`bundle.language.enableSplit = false`), because the app switches language itself and every install needs both English and Arabic. Always check a change that touches libraries with a release build on the emulator: sign the unsigned APK with the debug keystore (`apksigner sign --ks ~/.android/debug.keystore --ks-pass pass:android ...`) and `adb install -r`. The Play upload is signed with the user's upload key in Studio. Version 2.0 is versionCode 20 (the Play v1.2 build is 9); the release checklist and store texts are in `docs/RELEASE.md`.

## Modules

- `:domain`: pure Kotlin/JVM (no Android). `model/` (`Player`, `Cell`, `Board`, `GameConfig`, `GameState`, `GameResult`, `MatchState`, `BoardSize`, `Level`, `GameMode`, `Settings`, `ThemeMode`, `Starter`, `StatsKey`, `LevelStats`, `Stats`, `DailyChallenge`, `ChallengeProgress`, `Achievement`, `ChallengeReminder`, `ReminderSchedule`), `engine/WinChecker`, `ai/` (`SearchAi`, `DifficultyPolicy`, `ChallengeGenerator`), `multiplayer/` (two-phone play: `PeerChannel`, `PeerMessage`, `TwoPhoneRules`, `TwoPhoneState`, `TwoPhoneSession`), `repository/` interfaces (`SettingsRepository`, `StatsRepository`, `AdPolicyRepository`, `PurchaseRepository`, `ChallengeRepository`, `AchievementsRepository`, `PromptsRepository`, `TimeProvider`) and `usecase/` (game, settings, stats, daily challenge and achievements, review/update prompts, the daily reminder (`ReminderUseCases.kt`), and monetization: `ShouldShowInterstitialUseCase`, `GetAssistAccessUseCase`, purchase/restore/simulate Remove ads). Use cases have `@Inject` constructors so Hilt can build them. Tests in `domain/src/test`.
- `:data`: Android library with the repository implementations, bound in `data/di/DataModule`: settings, stats, ad policy, solved challenges, achievements and prompt times on Preferences DataStore files (`settings`, `stats`, `ad_policy`, `purchases`, `challenge`, `achievements`, `prompts`; one `@Singleton` per file, with qualifiers), and `PurchaseRepositoryImpl` on Play Billing 9.1 (product `remove_ads`) behind the internal `BillingGateway` interface (`PlayBillingGateway` is the real one; tests use a fake), and two-phone play on Nearby Connections (`nearby/`: `NearbyPeerLobby`, `NearbyPeerChannel`, `PeerCodec`, behind the internal `NearbyGateway`). Tests in `data/src/test` use temp DataStore files or an in-memory `FakeDataStore`.
- `:presentation`: Compose UI (Material 3), ViewModels (`@HiltViewModel`), type-safe Navigation Compose (`navigation/XoNavHost.kt`), theme (`theme/`, brand yellow `#D6BD17` / black, `sukar` font in `res/font`), English + Arabic strings (`values`, `values-ar`), the game screen (`game/`), Daily challenge (`challenge/`), Achievements (`achievements/`), Settings (`settings/`) and Stats (`stats/`) screens, sounds and vibration (`feedback/`, sounds in `res/raw`), the launch screen content (`splash/`), Play in-app review (`review/`) and updates (`update/`), the daily-challenge reminder (`reminder/`), its Hilt module (`di/`), the Remove-ads badge, dialog and shared purchase ViewModel (`purchase/`), the two-phone lobby, permissions and game screen (`twophones/`), and the ad/consent code (`ads/`). JVM tests in `src/test`, Compose UI tests in `src/androidTest`.
- `:app`: the application. `XoApplication` (`@HiltAndroidApp`; registers the `CurrentActivityTracker` that Play Billing needs to show its purchase sheet), the launcher `startActivities/splash`, the Compose `MainActivity`, and `di/` (binds `AdUnitIds` to `AppAdUnitIds`, which reads the resValue IDs, and the reminder's `AppIntents` to `AppIntentsImpl`). There are no XML layouts left.
- Dependency rule: `presentation → domain ← data`; only `:app` sees everything. Each module has its own `.gitignore` for `/build`.
- Compose-drawn brand graphics live in `presentation/components` (`drawX`/`drawO`, `XoLogo`, `BrandBackground`). The "XO" logo and the game board are forced LTR so they never mirror in Arabic.

AdMob IDs are set per build type in `app/build.gradle.kts`. The app ID goes into the manifest as `${admobAppId}`. Every placement has its own unit ID as a `resValue` string: `banner_<screen>`, `interstitial_<screen>`, and one shared `rewarded_vs_computer`. Screens are `main`, `easy/medium/hard_vs_computer` and `easy/medium/hard_level`; v1's easy/medium/hard screens were the 3×3/4×4/8×8 boards, so `AppAdUnitIds` maps mode + board to them (the computer's level doesn't change the unit) and AdMob reports stay comparable with v1. (`banner_x_or_o_dialog` was removed with its dialog in milestone 4; the unit still has to be deleted in the AdMob console, see `docs/UPGRADE_PLAN.md`.) Release has the real IDs (from Release_1.1). Debug uses Google's public test IDs for all of them. A blank ID crashes the app at startup. The `:presentation` UI test APK declares Google's sample app ID in `src/androidTest/AndroidManifest.xml` for the same reason.

Installing a local build on a device that has the Play Store build fails (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`; before 2.0 it was `INSTALL_FAILED_VERSION_DOWNGRADE`): the Play build has a different signing key. Uninstall it first. Only `startActivities.splash` is exported, so launch with `adb shell am start -n com.m7mdabaza.x_ogame/com.m7mdabaza.xogame.startActivities.splash`.

## Architecture

- The app is portrait only (`screenOrientation="portrait"` on both activities, a user decision). Android 16+ may ignore that on large screens, so `GameScreen` keeps a side-by-side layout for wide windows.
- Flow: `startActivities/splash` (launcher; shows `XoSplash` while UMP consent runs, at least 2 s) → Compose `MainActivity` → `XoApp` → `XoNavHost`: Home (+ `GamePickerSheet`, `presentation/home`) → `Destination.Game(mode, boardSize, level)` (`presentation/game`); Home also opens Stats, Achievements, Settings and the Daily challenge. The splash finishes itself; when the launcher reopens an existing task it closes again at once (`isTaskRoot` check) so the restored screens show instead of a second `MainActivity`.
- The splash activity (`@AndroidEntryPoint`) draws `XoSplash` from `:presentation` (`splash/SplashContent`: the Home logo, tagline and background), wrapped like `XoApp` in the theme root, so it follows the app's Light/Dark setting. Keep the class name `splash`: it is the exported launcher component, and renaming it breaks home-screen shortcuts. Both activities use `Theme.XoGame` (window background white, dark in `values-night`), which Android shows before the first frame and behind its own Android 12+ launch icon.
- **Board and level** are separate choices (milestone 10, user decision): `BoardSize` THREE (3×3, 3 in a row), FOUR (4×4, 4 in a row) or EIGHT (8×8, 5 in a row), and against the phone a `Level` EASY / MEDIUM / HARD for any board. `GameConfig.level` is required against the computer and null in two-player mode (checked in `init`). The picker sheet (`home/GamePickerSheet`): against the phone, board cards (radio choice) + a level row + Play, with the last choice remembered in `Settings.boardSize` / `level` (saved by `HomeViewModel.onGameChosen`); two players just tap a board.
- **Game screen** (one screen for every mode, board and level):
  - `GameViewModel` owns the match: setup, rounds, the computer's moves (`viewModelScope`, a short `COMPUTER_DELAY_MS` pause, then the search on the injected `@DefaultDispatcher`), undo, hints and the score. It reads `mode`/`boardSize`/`level` (enum names; `level` only against the computer) from `SavedStateHandle`, so the `Game` route's properties must stay plain strings named like `GameViewModel.ARG_MODE` / `ARG_BOARD_SIZE` / `ARG_LEVEL`. The title is "Easy · 3×3" against the phone and "3×3 board" for two players.
  - After every change the whole session is written to `SavedStateHandle` as JSON (`SavedSession`: settings, match score, the round's first player and its moves), so it survives rotation and process death; a round is rebuilt by replaying its moves.
  - `GameUiState.phase` is SETUP / PLAYING / ROUND_OVER / MATCH_OVER. Undo works only in PLAYING: a finished round (won, lost or drawn) is never undone (user decision). `GameScreen` is stateless (`GameUiState` + `GameActions`); `GameRoute` connects it to the ViewModel. `GameBoard` draws the grid, animated marks, the hint preview and the win line; every square is a clickable node with a content description. `MatchSetupDialog` picks symbol / names, who starts and the match length.
  - Matches (`domain` `MatchState`): Single is a running tally of independent rounds; best of 3/5 lasts at most N rounds (draws count) and ends early when the leader can't be caught. In a best-of match the players take turns to start.
  - Sounds and vibration go through the `GameFeedback` interface (fake in tests); `AndroidGameFeedback` is a singleton `SoundPool` + `Vibrator` that follows the sound / vibration settings (collected on the `@ApplicationScope` scope).
  - Finished rounds are recorded with `RecordGameResultUseCase` (from player one's side: the human, or X in two-player mode). Starting a match saves its choices (symbol, who starts, match length, names) in `Settings` as the next setup's defaults.
- **Settings, theme, language:** `XoApp` reads the theme setting through `XoAppViewModel` and passes `darkTheme` to `XoTheme`; marks use `XoTheme.colors` (O is light in dark mode), and system-bar icons follow the app theme. The whole UI sits in one `Surface`, which sets the default content colour. The language is not in DataStore: `AppLanguageController` uses AppCompat per-app locales (`AppCompatDelegate.setApplicationLocales`; `autoStoreLocales` service and `res/xml/locales_config.xml` in the app manifest). The "Privacy settings" entry (UMP) is in Settings, shown only when required.
- **Stats:** one `LevelStats` per `StatsKey` (wins, losses, draws, current and best win streak; a loss or draw ends a streak): mode + board + level against the phone, mode + board in two-player mode (DataStore keys like `VS_COMPUTER_EIGHT_HARD_wins` / `TWO_PLAYERS_THREE_wins`; older per-level keys from unreleased builds are ignored). In two-player mode wins/losses are X/O wins and streaks aren't shown. The Stats screen shows a board tab with a card per level against the phone, and a card per board for two players.
- **AI** (`domain/ai`): one alpha-beta engine (`SearchAi`) for all sizes over a window-counting `SearchBoard`; it always takes a win in one, blocks a loss in one (unless `Difficulty.missedBlockChance` makes it overlook it), is perfect on 3×3 at full strength and searches only the top pattern-ranked cells near existing marks on 8×8. `DifficultyPolicy.computer(board, level)` sets depth, candidate limit and mistake / missed-block chances; `hint(board)` is full strength. Calibrated head to head (`SearchAiTest` checks it): 3×3 Hard is perfect and never loses (user decision) while Easy and Medium stay beatable, Medium less often; 3×3 Easy and Medium also overlook threats (40% / 10%), so a beginner wins more than half the games against Easy and about 1 in 5 against Medium (user request: they used to block everything and felt unbeatable); 4×4 is a draw with sensible play, so there Easy and Medium overlook threats too; on 8×8 each level clearly beats the one below.
- **Two phones** (v3, in progress; `GameMode.TWO_PHONES`, `domain/multiplayer`, plan in `docs/UPGRADE_PLAN_V3.md`): each player on their own phone, connected nearby.
  - The host plays X and sends the setup. `GameConfig.humanSymbol` is this phone's mark, and stats count from this phone's side, with streaks. No undo, no hints.
  - `TwoPhoneRules` is a pure state machine both phones run on the same messages. `PROTOCOL_VERSION` must be equal on both phones, and `Hello` must keep its shape forever. Board-changing messages carry a `stage` counter.
  - While a request (restart / new match) waits, its sender can't move or continue. When both ask at once, the host's request wins. A restart lapses when the round ends first.
  - Change these rules only together with `TwoPhoneRulesTest`: its randomized test plays thousands of games with random delivery orders and checks both phones stay in sync.
  - Connecting (`domain` `PeerLobby`, `data/nearby`): Nearby Connections through the internal `NearbyGateway` (fake in tests).
    - Settings: point to point, `ConnectionType.NON_DISRUPTIVE` (Nearby never takes the phone off its Wi-Fi), and service ID `com.m7mdabaza.x_ogame.nearby`. Never change the ID, or versions stop finding each other.
    - The host advertises an `Announcement` (`version|board|length|name`) and accepts or declines each request; both phones show Nearby's 4-digit code. The guest searches, stops searching to join, and accepts its own side.
    - `NearbyPeerLobby` is a singleton. The connection outlives the lobby screen, and the game ends it with `PeerChannel.close()`, which waits for the goodbye to arrive.
    - Messages are JSON (`PeerCodec`).
  - Permissions: the manifest entries are in `data/src/main/AndroidManifest.xml`; the runtime ones per Android version are in `presentation/twophones/NearbyPermissions`.
    - Location is requested up to Android 12L, and Location must be on up to Android 11.
    - `ACCESS_WIFI_STATE` is declared for every version: the guide says up to API 32, but Nearby refused to advertise without it on Android 17.
    - The library's Exposure Notifications `WakeUpService` is removed in the app manifest.
  - Testing on emulators: two `-read-only` instances of the same AVD can find and connect to each other over emulated Bluetooth (`emulator -avd Medium_Phone_API_37.0 -read-only -port 5554`, again with `-port 5556`; every instance must be read-only). Grant the permissions with `adb shell pm grant`, or tap through them. In Git Bash, `MSYS_NO_PATHCONV=1` helps `adb shell` paths but breaks `./gradlew`, so don't export it.
- **Daily challenge** (`presentation/challenge`): an 8×8 "win in 2" puzzle, X to move. `ChallengeGenerator` builds it from the local date alone (a seeded random game until a clean position with 1–3 fork moves appears), so it's the same on every phone and nothing is stored. Changing the generator changes future puzzles. `TimeProvider.todayEpochDay()` gives the local day (java.util, since java.time needs API 26). A first move that isn't a solution fails at once; otherwise the computer (Hard) blocks one threat and the player must take the other. Retries are unlimited; only solved days are stored (`ChallengeRepository`), and the streak is consecutive solved days up to today or yesterday.
- **Achievements** (`domain/model/Challenge.kt` `Achievement`, `presentation/achievements`): 8 local achievements, progress derived from `Stats` and the challenge history ("beat Medium/Hard" count wins on any board, "5 in a row" means on one board and level). `EvaluateAchievementsUseCase` runs after every finished round and every solved challenge and returns the new unlocks, which the screen shows as snackbars; Home runs it silently on open. Unlock times are stored separately (`AchievementsRepository`), so achievements survive a stats reset. Unknown stored keys are ignored, so an achievement can be removed safely; a new one unlocks silently for players who already qualify.
- **Play in-app review** (`presentation/review`, review-ktx): asked only at a happy moment (the human beat the phone, `GameState.humanBeatComputer`, or solved the daily challenge), after at least 5 finished games and at most every 90 days (`ShouldRequestReviewUseCase`; times in `PromptsRepository`). The ViewModels send `GameEvent.RequestReview` / `ChallengeEvent.RequestReview`; the route calls `rememberInAppReview()`. Play has its own quota and never reports the outcome; without Play nothing shows.
- **Daily-challenge reminder** (`presentation/reminder`, user decisions 2026-11-05): a notification 24 hours after the app was last opened, then every 24 hours while it stays closed (at most `ReminderSchedule.MAX_IN_A_ROW` = 7), never between 22:00 and 09:00 (moved to 09:00), and quiet on days the puzzle is already solved.
  - `MainActivity.onStart` calls `ChallengeReminderScheduler.onAppOpened()`, which removes a shown reminder and replaces the one unique WorkManager job (`daily_challenge_reminder`). `ChallengeReminderWorker` (Hilt via `ChallengeReminderEntryPoint`) asks `OnChallengeReminderDueUseCase` what to do, shows it and appends the next job. The setting (`Settings.challengeReminder`, on by default) is checked when the job runs, so the Settings switch doesn't touch WorkManager.
  - Texts: `ReminderTexts` rotates by date through 16 daily texts, 8 streak texts (plurals, when a streak of 2+ days is at stake) and 4 "comeback" texts (3rd reminder in a row), English + Arabic. To add one, add its strings and a line there. Only emojis that Android 7 can show.
  - Language: the app's language tag travels in the job's input data, because below Android 13 a worker can't read the AppCompat per-app language; `ChallengeReminderNotifier` builds a context in that locale.
  - Permission (Android 13+): asked once ever, on Home at startup (`AskNotificationPermissionOnce`, time in `PromptsRepository`). The Settings switch shows on only if the setting and the system both allow it; turning it on asks again, or (after two refusals or with notifications blocked) shows a snackbar that opens the system notification settings.
  - A tap opens `splash` with `ACTION_OPEN_DAILY_CHALLENGE`: on a cold start it runs the consent flow and passes the action on; with the app running it forwards to the existing `MainActivity` (`CLEAR_TOP | SINGLE_TOP`, `onNewIntent`). `XoNavHost` then opens the Daily challenge on top of Home.
  - To see a reminder without waiting, background the app and run `adb shell cmd jobscheduler run -f -n androidx.work.systemjobscheduler com.m7mdabaza.x_ogame <id>` (the id is in `adb shell dumpsys jobscheduler | grep ChallengeReminder`).
- **Play in-app updates** (`presentation/update/InAppUpdates`, app-update-ktx): on Home, a flexible update is offered at most every 3 days (`ShouldPromptForUpdateUseCase`); once downloaded a "Restart" snackbar installs it (offered again on the next start if dismissed). Without Play the check fails quietly. Tested with `FakeAppUpdateManager` in `InAppUpdatesTest`; a real check needs two builds on a Play testing track.
- Route event handlers launch snackbars and the review sheet in their own coroutines, so a 4-second snackbar never holds up the next event (like an interstitial).
- Ads (Google Mobile Ads SDK 25). Banner and interstitials stop once Remove ads is bought; rewarded ads stay available for extra hints/undos:
  - Banner: Compose `BannerAd` (large anchored adaptive) on Home, the game screen and the Daily challenge (it uses the Home unit). Its height varies, so snackbars live inside the content area above it, never over the ad.
  - Interstitial: only between rounds, when `ShouldShowInterstitialUseCase` allows it (not before round 2 of a session, at least 2 rounds and 3 minutes since the last one; counts in `AdPolicyRepository`). The ViewModel decides when a round ends (`interstitialDue`) and sends `GameEvent.ShowInterstitial`; `GameRoute` shows it and calls `onInterstitialFinished`.
  - Rewarded: pays for hints and vs-computer undos (`GetAssistAccessUseCase`: undo is free in two-player mode; Remove-ads buyers get one free hint and one free undo per round, not reset by Restart). The player first confirms a "watch an ad?" dialog; the reward is given only if the ad was watched to the end.
  - `presentation/ads/AdManagers.kt` (`InterstitialAdManager`, `RewardedAdManager`) load ahead of time and report back when the ad closes.
  - Remove ads: Settings shows the price (from Play), Restore purchases, and in debug builds a "Simulate Remove ads" switch (`PurchaseRepository.setAdsRemovedForDebug`, ignored in release). On devices without a signed-in Play account billing is unavailable and the button is disabled; a real purchase needs the `remove_ads` product in Play Console and an install from a testing track.
  - "No ads" badge (`presentation/purchase`, v3 milestone 1): a yellow pill in the top bar of Home, the game screen and the Daily challenge that opens `RemoveAdsDialog` (benefits, Buy for {price}, Restore purchases, Not now). It shows only while ads aren't removed **and** Play returns a price (`RemoveAdsUiState.showBadge`), so debug installs and emulators without a Play account never show it. To see it there, temporarily give `RemoveAdsViewModel` a placeholder price. In title bars it drops its label from font scale 1.5. `RemoveAdsViewModel` is the one place for purchase/restore results (Settings uses it too): a result with a message closes the dialog and shows a snackbar on that screen, while a cancel leaves the dialog open. Each route gets its own instance (`hiltViewModel()`) plus `RemoveAdsDialogHost`; the stateless screens only take `showRemoveAdsBadge` + an `onRemoveAds` action. The "Remove ads" link in the hint/undo ad offer opens the same dialog.
- EU consent uses Google UMP (`presentation/ads/ConsentManager.kt`). `splash` calls `gatherConsent()` and waits for it before opening `MainActivity`. Every ad request is gated on `canRequestAds()`: banners go through `AdView.loadAdIfAllowed()` (the Compose `BannerAd` uses it too), and the AdManagers check it in `load()`. Don't call `MobileAds.initialize` or `adView.loadAd` directly. The Settings screen shows a "Privacy settings" entry only when UMP says privacy options are required. Debug builds force EEA geography, so the form shows on emulators. The real message text is configured in AdMob → Privacy & messaging.
- Compose UI tests need Espresso 3.7 pinned in `:presentation` (Compose testing pulls in 3.5, which crashes on API 34+).
- **Accessibility and RTL rules** (milestone 7; `AccessibilityTest` runs Google's Accessibility Test Framework over every screen, so new UI should pass it):
  - Controls drawn without text (X/O marks) need a `contentDescription`; groups read as one item use `clearAndSetSemantics` (scoreboard chips, stat cells); titles get `heading()`.
  - Text choices use `TextChoices` (one line that auto-shrinks down to 9 sp, so nothing is cut off at 2× font); action rows use equal-weight tiles; avoid fixed heights around text.
  - Board squares are full-size touch targets; the 8×8 board uses almost the full width (squares about 50 dp on a 411 dp phone, about 44 dp on 360 dp phones; the user accepted that, no zoom).
  - Player names go into sentences through `isolated()` (`BidiFormatter`), so Arabic and Latin names don't reorder the text. Don't put raw bidi control characters in code (lint BidiSpoofing).
  - Numbers stay Western digits in both languages; percentages use the `stats_percent` resource (Arabic uses ٪).
  - The splash uses the Home tagline (`home_tagline`, translated); `app_name` is the brand and not translated. The launcher icon has English text baked in.
